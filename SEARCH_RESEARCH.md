# Исследование поиска ETSI / 3GPP

Дата: 5 ноября 2026. Цель: точная выдача по номеру, названию, разделу и термину
с проверяемым фрагментом, без внешнего сервиса и без JavaScript на клиенте.

## Вывод

Универсально «наиболее качественного» поискового алгоритма для любого корпуса
нет. Для 3GPP разумная базовая система — отдельная обработка идентификаторов,
поиск по полям, BM25F и фрагменты с реальными совпадениями. Система с более
высоким потолком качества: lexical + learned sparse/dense candidates → fusion
→ cross-encoder reranking. Её выигрыш нужно измерить на запросах и оценках
релевантности именно этого корпуса; техническая сложность не доказывает качество.

## Прочитанные первичные источники

1. Robertson, Zaragoza. [The Probabilistic Relevance Framework: BM25 and Beyond](https://www.staff.city.ac.uk/~sbrp622/papers/foundations_bm25_review.pdf), 2009, §§3.4, 3.6, 3.8, 5.
   BM25 нормализует частоту по длине текста и использует IDF. BM25F объединяет
   поля с разными весами. Это обосновывает раздельные признаки заголовка и тела;
   простая сумма всех упоминаний приводит к преимуществу длинных разделов.
2. Thakur et al. [BEIR](https://arxiv.org/abs/2104.08663), NeurIPS 2021.
   На разнородных задачах BM25 оказался сильной базой; reranking/late interaction
   часто дают больше качества при больших вычислительных затратах. Результаты
   этого исследования не являются рейтингом современных моделей на 3GPP.
3. Chen et al. [M3-Embedding](https://aclanthology.org/2024.findings-acl.137/), ACL 2024.
   Один подход поддерживает dense, sparse и multi-vector retrieval. Подходит как
   кандидат для следующего экспериментального этапа, а не как автоматическая
   замена точных номеров и аббревиатур семантической похожестью.
4. Lassance et al. [SPLADE-v3](https://arxiv.org/abs/2403.06789), 2024.
   Learned sparse retrieval — альтернативный кандидат для расширения охвата.
   Нужны модель, отдельный индекс и собственная оценка стоимости/качества.
5. Elastic: [Highlighting](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/highlighting).
   Совпадения нужно привязывать к исходным смещениям текста. Лучшие фрагменты
   выбираются по совпадениям, а не как первые N символов. Подсветка сама по себе
   не доказывает выполнение логики запроса — проверка отбора остаётся отдельной.
6. Elastic: [Reciprocal rank fusion](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion),
   [Semantic reranking](https://www.elastic.co/docs/solutions/search/ranking/semantic-reranking).
   Fusion объединяет кандидатов разных retriever; reranking — следующий этап.
   Пагинацию необходимо проверять отдельно при фиксированном списке кандидатов.

## Что реализовано сейчас

- Единица результата: совпадение названия/номера спецификации или конкретного
  раздела. От одной спецификации может быть любое количество результатов.
- Единая сортировка всех результатов, по умолчанию **5 на страницу**. Есть
  переключатель 5/10/20/50/100, а не количество превью на спецификацию.
- При указанном поколении сначала учитываются технология и тема раздела
  вместе с его настоящей цепочкой родительских глав. LTE/5G из общей шапки
  документа — слабое доказательство. E-UTRAN не считается обычным UTRAN.
- Внутри соответствующего контекста: точный номер → название спецификации
  → точное название раздела → все/часть слов в заголовке → тело. Сам по себе
  короткий заголовок Attach не получает преимущество перед основной процедурой.
- Для общего запроса специальные сценарии (LI, RN, PMIP, SRVCC, V2X и т.п.)
  вторичны. Если такой сценарий прямо указан в запросе, его приоритет возвращается.
  Это явные признаки 3GPP-контекста, без зафиксированных номеров спецификаций.
- Родительские заголовки читаются пакетами по составному индексу; полные тексты
  для определения контекста не сканируются. Схема и индексатор не меняются.
- Внутри приоритета: BM25F, полнота совпадения, фраза в заголовке, особенности
  обзорного/начального описания процедуры и специализированных подразделов;
  при равенстве — число упоминаний и устойчивые идентификаторы.
- BM25F по разделу: k1=1.2, вес заголовка=4, b_body=0.65, b_title=0.3,
  IDF из term_stats. Для группы словоформ DF оценивается суммой DF с ограничением
  размером корпуса. Это приближение для объединения вариантов; для одного
  буквального слова используется его собственный DF.
- Средние длины считаются по существующему индексу и кешируются на 60 секунд.
  Новые результаты не кешируются: они доступны сразу; средние длины обновляются
  с задержкой до минуты. Сам индекс и схема базы остаются v3.
- Числовой score — составной вес приоритета и лексической оценки, не вероятность.
  Стартовые коэффициенты — инженерный выбор, а не доказанные оптимальные веса.
- История изменений и списки ссылок исключены из обычного поиска. По явному
  change history история доступна. Пары из глоссария — отдельная страница.
- Нормализация NFKD применяется и при подборе фрагмента. Смещения ведут к
  исходному тексту: сохраняются диакритики, регистр, пунктуация и full-width.
- Фрагмент без совпадений **не выводится**. Если термин только в заголовке,
  показывается этот заголовок и указание поля, где найдено совпадение.
- Подсветка — <strong> вокруг реально найденных слов. Источники и запросы
  экранируются Jinja; пользовательский HTML не помечается как safe.
- Если найден вариант (register → registration, 4g → EPS), это явно указано
  в Related terms. Нельзя выдать EPS за буквальное появление строки 4g.
- Search within results пересекает результаты по идентификаторам разделов,
  включая результаты на остальных страницах. Совпадение номера/названия всего
  документа задаёт область документа. Новые совпадения из постороннего раздела
  той же спецификации не подмешиваются. Глубина уточнения до четырёх шагов.
- Сохраняются прямые PDF-ссылки на печатную страницу + 1 и путь до главы.

Отбор работает по редкому слову и точечным postings-пробам. Для обычного запроса
хранится только глобальный top-(page × page_size); тела читаются только для
страницы. Уточнение временно хранит идентификаторы подходящих разделов.
Полные тексты не сканируются для подсчёта частот.

## Что следует проверить до добавления нейросетевого этапа

1. Разметить 100–300 запросов: номера, заголовки, аббревиатуры, процедуры,
   несколько слов, опечатки, запросы по поколениям, редкие и общие термины.
2. Оценивать конкретные результаты (spec + clause), а не только наличие нужной
   спецификации. Релевантность 0/1/2/3; спорные примеры проверять экспертно.
3. Отложить часть запросов; сравнить nDCG@5/10, MRR@5, Recall@50, p50/p95,
   объём индекса, память. Настройку весов проводить на другой части запросов.
4. Сравнить текущий BM25F с hybrid RRF и cross-encoder top-50/100. Сохранить
   обязательные точные ID/аббревиатуры и запрет неподтверждённого фрагмента.
5. Затем выбирать систему по измеренному качеству/стоимости. Без такой оценки
   утверждение «семантический поиск лучше» не проверено.

## Проверка этой реализации

Регрессионные тесты: глобальный размер страницы, несколько результатов из одной
спецификации, монотонность веса и отсутствие повторов на неизменном корпусе,
фильтрация внутри реальных разделов, приоритет заголовка над тысячами повторов,
фрагмент только с подтверждённым совпадением, Unicode, словоформы, XSS и PDF page+1.
Интеграция расширена до 15 реальных спецификаций: исходные 23.401, 24.301,
23.501, 23.502, GSM 04.08 и конкуренты из полной пользовательской выдачи:
23.402, 23.236, 33.128, 23.272, 23.139, 36.300, 24.008, 23.119, 23.216, 23.285.
Регрессия воспроизводит короткие Attach, LI, RN, GPRS/IMSI и CS fallback.
Для 4g attach первым должен быть 23.401 §5.3.2.1 E-UTRAN Initial Attach. Это функциональные проверки, не размеченный
бенчмарк полного корпуса ETSI; чисел nDCG для полного корпуса не заявляем.
